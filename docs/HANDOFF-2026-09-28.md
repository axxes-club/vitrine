## Why sign-in is broken (and what fixed it)

The symptom was Safari's "Too many redirects" on `vitrine.axxes.club/admin`, which
is a *different* bug from the email casing and was masking it.

The loop:

```
vitrine.axxes.club/admin
  -> getContext() finds no valid session
  -> 307 to handshake.axxes.club/sign-in?redirect=...
  -> Handshake DOES see the session, so it redirects straight back
  -> vitrine finds no session again
  -> forever
```

`handshake.axxes.club/src/app/sign-in/page.tsx:17` is the bounce:
`if (await getSession()) redirect(next)`.

**Root cause:** Handshake and Vitrine had independently generated
`BETTER_AUTH_SECRET` values, so each signed/verified the session cookie with a
different key. The apps agreed locally (the `.env.local` files match) and only
production drifted — Vitrine's production env was created ~4h after Handshake's.

**Fix applied:** one `BETTER_AUTH_SECRET` and `AUTH_COOKIE_DOMAIN=.axxes.club`
across handshake, vitrine and members. Set in Vercel, but **env only takes effect
on a deploy** — that deploy is what the cap is blocking.

**Why it is worse right now:** handshake is deployed with the NEW secret, vitrine
is not. They are guaranteed to disagree until vitrine redeploys. There is no
client-side workaround: signing out and back in recreates a cookie vitrine still
cannot read.

## Dead ends — do not repeat these

- **Comparing production secrets via `vercel env pull`.** Every value comes back
  `[SENSITIVE]`, so every pair "matches". This produced a false all-clear before
  the real cause was found. Compare by *behaviour* or by hashing a value you set
  yourself, never by reading back a secret.
- **Testing case-folding with a guessed password.** The control case 401'd too, so
  the test proved nothing. Always verify the control works before trusting a
  failure. The case bug was eventually proven by comparing the stored string to the
  typed one, not by logging in.
- **Assuming "our board" exists.** AXXES CLUB had six members and **zero** boards;
  four other orgs had `project_lists` with no matching `projects` row (orphans,
  still unexplained).
